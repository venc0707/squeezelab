# Решения проекта SqueezeLab

Источник истины по архитектуре и решениям — MASTER CHAT. Этот файл — копия состояния для
репозитория (Phase 00, дополнен в Phase 01). Рабочий чат решений не принимает: открытые пункты
остаются OPEN до ответа пользователя.

Версия состояния проекта: 1.4 (дата: 2026-11-17).

### Принято в Phase 01, P01-T01 (реализация; мастер-чат может пересмотреть)

| # | Решение | Причина |
|---|---|---|
| B-12 | `strategy_hash(cfg)`: sha256 канонического JSON секций presets, exits, risk, symbols; `app_hash(cfg)`: sha256 JSON всего `app.yaml` (режим, пути, рекордер, логи). Функция `config_hash` удалена, чтобы старое имя не использовали по ошибке. `config check` печатает оба; тестовое сообщение Telegram содержит оба. Эталоны закреплены в тесте `test_repo_hashes_are_pinned`. `SQUEEZELAB_DATA_DIR` ни в один хэш не входит, а правка `paths.data_dir` меняет `app_hash` | Смена пути или уровня логов не должна менять идентификатор стратегии в журнале; одинаковые хэши на ПК и сервере остаются проверяемыми |
| B-13 | Единая фабрика `app/http_clients.py`: BingX всегда `trust_env=False`; Telegram `trust_env=False` и явный `proxy`. По коду httpx 0.28.1 `trust_env=False` отключает ещё чтение `SSL_CERT_FILE` и `SSL_CERT_DIR` (и `~/.netrc`): клиенты используют сертификаты certifi, корпоративный корневой сертификат пришлось бы передавать явно. Если `proxy` задан, httpx использует его вместо `transport`: в тестах с mock-транспортом прокси не задаётся | M-04; единственное место создания `httpx.Client` |
| B-14 | `TELEGRAM_PROXY_URL` в `.env`: `SecretStr` (в адресе бывают логин и пароль), маскируется в логах, команды печатают только «задан / не задан». Допустимы схемы `http` и `https` (локальный Xray: `http://127.0.0.1:10809`); `socks5` не принимается, потому что требует доп. пакет `httpx[socks]`. Текст ошибки проверки не содержит значения. Пустое значение = не задан | Прокси нужен только Telegram; пароль не должен попасть в вывод |
| B-15 | Секреты по областям: `TelegramSecrets`, `BingXSecrets`, `Secrets` (обе); `load_telegram_secrets` для `notify-test` и будущего рекордера, `load_bingx_secrets` для `bingx-auth-check`, `load_secrets` только для `config check`. В объект области значения чужой области не попадают, даже если заданы в `.env` или окружении, а ошибка в чужой переменной (например, `BINGX_ENV=prod`) не мешает | Наименьшие привилегии: рекордер не видит ключи BingX |
| B-16 | `resolve_data_dir()`: переменная → `paths.data_dir` → `./data`. `paths.data_dir` стал необязательным (не задан = `./data`). Относительный путь считается от текущего каталога процесса, `~` раскрывается, пустая переменная = не задана; каталог не создаётся. Переменная читается только из окружения процесса, не из `.env` (как `SQUEEZELAB_CONFIG_DIR`); на сервере её выставит systemd-юнит | M-05 |
| B-17 | Раздел `recorder` в `app.yaml`: `symbols` (по умолчанию `[BNB-USDT]`, вид как в `symbols.yaml`, без дублей), `oi_interval_s` и `funding_interval_s` (по умолчанию 60, допустимо 10–3600). Нижняя граница 10 с поставлена рабочим чатом как защита от шквала запросов (лимит биржи 500 за 10 с). Остальные настройки рекордера (порог «немого» потока, порог `gap`, доля диска) добавит P01-T05; настройки загрузчика, если понадобятся, P01-T02 | M-06 |
| B-18 | Блокировка режимов: `priority` блокирует `paper_vst` и `live` и не блокирует `backtest`. Остальные `null` в risk.yaml и exits.yaml блокируют все режимы кроме `signals_only`, включая `backtest`, как и раньше: мастер сказал только про `priority`. Следствие и вопрос мастеру: см. вопрос 11 ниже | M-03 |

### Принято в Phase 01, P01-T02 (реализация; мастер-чат может пересмотреть)

| # | Решение | Причина |
|---|---|---|
| B-19 | Хранилище свечей (`data/store.py`): Parquet через pyarrow 26.0.1 (сжатие zstd), помесячные файлы `{data_dir}/candles/{symbol}/{tf}/{YYYY-MM}.parquet`, месяц по UTC, одна схема `ts_open` int64, `o h l c v` float64. Запись атомарна (временный файл рядом, `fsync`, `os.replace`); слияние идемпотентно (повторная запись тех же данных файл не трогает); при расхождении значений для того же `ts_open` побеждают новые, и это видно в статистике как `updated`. Повреждённый файл или чужая схема дают `StoreError` и не затираются. pyarrow не поставляет типов: для него в `pyproject.toml` стоит `ignore_missing_imports`, граница изолирована в `store.py` | Задание P01-T02; правило 4 (данные не удаляются) |
| B-20 | Пагинация загрузчика: окна `[start, end)` встык по `WINDOW_BARS = 1000` баров (настраивается `--window-bars`). Окно не усекается, потому что биржа при окне шире предела молча отдаёт самые новые свечи: для 15m не больше 1000, хотя `limit` до 1440 принимает; для 1m предел не меньше 1440 (раздел 4 `bingx_api_notes.md`). Единое окно 1000 безопасно для обоих ТФ Полнота окна проверяется по набору меток времени, до 3 попыток на окно. Повторный запуск пропускает окна, целиком лежащие в хранилище | Наблюдения пробы 2026-11-20 (G); ничего не принимается на веру |
| B-21 | Закрытость свечи определяется дважды: по часам машины и по самой новой свече, которую отдаёт биржа (она формирующаяся). Берётся более ранняя граница; если часы спешат, отчёт печатает «ВНИМАНИЕ». Формирующаяся свеча не сохраняется. Стоимость: один дополнительный запрос на пару и таймфрейм за запуск | Принцип «только закрытые свечи»; сбитые часы не должны дать недозакрытую свечу в данных |
| B-22 | Лимит частоты загрузчика 5 запросов в секунду (требование задания; лимит биржи 500 за 10 с), равномерные паузы без накопления «кредита» после простоя; один ограничитель на весь запуск команды | Запас относительно лимита биржи |
| B-23 | Пропуски не заполняются и не помечаются в P01-T02: отчёт перечисляет их (`ПРОПУСКИ (N)`), команда завершается с кодом 0 и предупреждением; окно с пропусками запрашивается не больше 3 раз за запуск, но заново при следующем. Пометку «подтверждённо отсутствует» и проверки добавит P01-T03 | Граница между задачами T02 и T03 |
| B-24 | Накопленное сбрасывается на диск каждые 10 окон и при любом выходе, в том числе по ошибке API (код 1, повторный запуск продолжает с места остановки). Свеча не по сетке ТФ или вне окна отбрасывается и считается в отчёте | Долгая загрузка 1m не должна терять прогресс |
| B-25 | Диагностическая команда `bingx-probe-klines` (два набора: `basic` и `paging`) добавлена рабочим чатом, чтобы факты о границах, порядке и пределе ответа брались из реальных запросов (правило 3). Её выводы печатаются по наблюдениям, без догадок; результат внесён в раздел 4 `bingx_api_notes.md` | Правило 3: факты об API подтверждаются реальным ответом |
| B-29 | Проверки качества (`data/quality.py`, `data check`): читает файлы месяцев «как лежат» (без слияния), чтобы увидеть дубли и беспорядок. Девять проверок на ряд: файлы читаются и схема верна; свеча в файле своего месяца; время растёт внутри файла; нет повторов `ts_open`; время на сетке ТФ; значения корректны (high не ниже open и close, low не выше, `low <= high`, цены > 0, объём >= 0, нет NaN и бесконечностей); нет пропусков между первой и последней свечой; подтверждённо отсутствующие (предупреждение); последняя свеча закрыта по часам машины. Кросс-проверка: крупный ТФ против агрегата из мелкого (open первой, close последней, max high, min low, сумма объёма), по умолчанию 15m:1m, другие через `--cross 1h:15m`; допуск цены 1e-9, объёма 1e-6; крупные свечи без полного набора мелких пропускаются и считаются. Отчёт в markdown `{каталог данных}/reports/quality_{ГГГГММДД_ЧЧММСС}.md`, итог в консоль. Код выхода 1, если есть ошибки или расхождения при кросс-проверке; предупреждения его не меняют. «Чистый» в приёмке = нет ошибок и расхождений | Задание P01-T03 |
| B-30 | Докачка и реестр пропусков (`data/sync.py`, `data sync`, вызывается из `data download`): пропуск запрашивается узкими окнами по 100 баров (окно не усекается: предел ответа 15m 1000), до 3 попыток; если свеча не пришла и ей больше 6 часов, слот пишется в `confirmed_missing.json` рядом с файлами месяцев («подтверждённо отсутствует»). Такие слоты не запрашиваются, окно загрузчика с ними считается полным, `data check` показывает их предупреждением, а когда свеча всё же попадает в хранилище, пометка снимается сама. Свежие пропуски не подтверждаются (биржа могла не дозаполнить). Допущение: предел ответа не меньше 100 свечей (наблюдалось 1000) | Задание P01-T03; иначе пропуск запрашивался бы вечно |
| B-31 | Слои хранилища (M-08): нативные свечи в `candles/`, ресемпл в `candles_resampled/` с той же раскладкой; `CandleStore(data_dir, layer=…)` и свойство `src` (`native` или `resampled`). Слои не смешиваются: читающий API `data/reader.py` (`CandleReader.read(..., src="auto"\|"native"\|"resampled")`) возвращает `SourcedCandle(candle, src)`; `auto` берёт нативные свечи, а ресемпл подставляет только в слоты без нативной. Вместо колонки `src` выбран каталог: файлы T02 не меняются, миграции нет | Происхождение видно по месту хранения и по ответу API |
| B-32 | Ресемпл (`data/resample.py`, `data resample [--from 1m] [--to 15m]`): корзины по границам крупного ТФ в UTC от эпохи, только полные (15 из 15 минуток); агрегат: open первой, close последней, max high, min low, сумма объёма. Неполные корзины (дыры в 1m) заносятся в реестр слоя как «не собирается» (`attempts=0`): `data check` показывает их предупреждением, а после `data sync` повторный ресемпл собирает корзину и пометка снимается сама. ### D-04 и D-05: закрыты

Пользователь выбрал **one-way** и **isolated** (2026-11-13). В one-way на паре существует одна
чистая позиция, а изолированная маржа ограничивает потерю маржой этой позиции. Детали поведения
биржи в этих режимах подтвердить на VST в Фазе 7; проверка, что цена ликвидации заметно дальше
стопа, остаётся требованием Фазы 6.

### D-09: пресеты на одной паре в one-way (частично решено)

Замечание пользователя: lvl6 и lvl3 работают на одной паре, а в one-way встречные сигналы
схлопываются в одну позицию. Что уже есть в плане (раздел 11.3): одноимённые сигналы
с пересекающимися отрезками образуют один кластер; противоположные стороны на одной паре дают
SKIP; при открытой позиции вторая не открывается.

**Решено пользователем (2026-11-13), C-03:** встречный сигнал при открытой позиции — **разворот
позиции**. Это расширяет план: у позиции появляется причина выхода «встречный сигнал».

**Решено пользователем (2026-11-14), C-04:** «одновременные» встречные сигналы — обнаруженные на
одном закрытом 15м баре. Если на одном баре пришли сигналы обеих сторон, ничего не делается: ни
входа, ни разворота, открытая позиция живёт по своим стопу и тейкам, всё пишется в журнал.
Одноимённые сигналы lvl6 и lvl3 на одном баре конфликтом не считаются (это один кластер).
Сигнал противоположной стороны на более позднем баре при открытой позиции — разворот (C-03).

**Не определено, нужно решить до Фазы 6** (рабочий чат ответов не придумывает):

1. Разворот делается сразу по рынку на баре обнаружения встречного сигнала?
2. Проходит ли встречный сигнал обычный отбор (score, veto, фильтры ширины стопа) до разворота?
   Если не проходит: позицию всё равно закрыть или держать до своего стопа и тейков?
3. Работает ли разворот на любой стадии: до TP1, после TP1 и переноса стопа в безубыток,
   после TP3 и т. д.? Результат закрытия при развороте считается в R как обычный выход.
4. Какой пресет вправе развернуть позицию: любой или только тот, что её открыл?
5. Как закрывается позиция: старые SL и тейки отменяются, остаток закрывается по рынку, затем
   отдельный вход с новым стопом и лесенкой.

Предложения рабочего чата (не решения):

- **Пункт 5.** Разворот в два шага (закрыть и дождаться нулевой позиции по бирже, затем войти):
  журнал и расчёт R остаются чистыми, вход защищён проверкой «позиция по паре равна нулю».
  Одним удвоенным ордером не делать: R, стоп и лесенка нового входа считаются от его собственной
  цены.
- **Бэктест (Фаза 4)** должен считать вариант с разворотом и без него: разворот — гипотеза, её
  проверяет сравнение, а не предпочтение.
- D-01 (приоритет пресетов) можно не решать до Фазы 4: матрица пересечения покажет, насколько
  пресеты различаются на одинаковых сигналах.
