# Заметки по API BingX

Каждый факт помечен одной из меток:

- **[проверено запросом]** — получено реальным ответом биржи (лог команды приложен в отчёте);
- **[по документации]** — взято из описания API (официальный репозиторий BingX-API, документация
  docs-v3, SDK) или из сторонних источников; в запросе не проверялось;
- **[не подтверждено]** — источники расходятся или фактов нет.

Состояние на 2026-11-13 (вторая серия запусков пользователя, Windows, без VPN): строки с меткой **[проверено запросом]** подтверждены его запусками `bingx-smoke`, `bingx-auth-check` и присланным фрагментом реального ответа. Рабочий чат сам к BingX не обращался (из его окружения DNS не разрешается).

Что клиент делает с этим сейчас (`src/squeezelab/data/bingx_rest.py`):

- парсер принимает только описанную форму (список объектов с шестью полями) и падает с понятной
  ошибкой на любой другой, а не угадывает формат;
- порядок ответа не предполагается: `sort_candles` возвращает новый список по возрастанию `ts_open`;
- ретраи только для GET: сетевые ошибки, HTTP 429 и 5xx, пауза 0,5 с × 2^n, но не дольше 30 с;
  `Retry-After` учитывается (не больше 60 с); ошибки 4xx и `code != 0` в теле не повторяются.

Оставшиеся непроверенные строки перечислены в разделе 3.

## 2. Подпись запросов и доступ только на чтение (P00-T05)

| Факт | Значение | Метка |
|---|---|---|
| Адрес демо-среды VST | `https://open-api-vst.bingx.com`; подписанный запрос принят | [проверено запросом] |
| Какой ключ нужен для VST | **ключ основного аккаунта** из обычного раздела API Management; отдельного раздела или переключателя для демо-ключей нет | [проверено запросом] (запрос принят; со слов пользователя про раздел). Следствие: тот же ключ действителен и на боевом контуре, поэтому ключ обязан быть только на чтение |
| Заголовок ключа | `X-BX-APIKEY: <ключ>` | [проверено запросом] |
| Параметры подписи | бизнес-параметры + `timestamp` (мс) + `recvWindow` (мс, в клиенте 5000) | [проверено запросом] для запроса без бизнес-параметров |
| Строка для подписи | `k=v` через `&`, ключи в порядке ASCII, без URL-кодирования | [проверено запросом] для `recvWindow` и `timestamp`; с другими параметрами не проверялось |
| Подпись | hex-HMAC-SHA256 от этой строки секретом API, параметр `signature` — последним | [проверено запросом] |
| Баланс | `GET /openApi/swap/v3/user/balance`; на VST в `data` один актив `VST`, поля `balance`, `equity`, `availableMargin` (100000.0000) | [проверено запросом]; форма (список или объект) парсером принята, какая именно — не фиксировалась |
| Актив демо-баланса | `VST` | [проверено запросом] |
| Права ключа | `GET /openApi/v1/account/apiPermissions`: ответ без поля `code`, плоский объект `{permissions: list[int], ipAddresses: list, note: str, apiKey: str}`. Реальное значение у ключа пользователя на VST: `permissions=[2]`, `ipAddresses=[]` | [проверено запросом] форма и эти значения. Что означает код `2` и остальные, **не подтверждено**; результат ручной проверки прав в API Management пользователь пришлёт отдельно. Команда печатает значения (целые и списки целых; строки `note` и `apiKey` скрыты) и напоминает про ручную проверку, выводов о правах не делает |
| Коды ошибок | в код не зашиты; `code` и `msg` печатаются как есть | сознательно: коды из памяти не использовались |

Заметки по реализации:

- Порядок ключей в строке подписи. В старых официальных примерах `timestamp` дописывается после
  отсортированных бизнес-параметров, в новых справочниках сортируется вместе со всеми. Разница
  проявляется только для ключей, которые по алфавиту идут после `timestamp` (например `type`,
  `workingType`). Запросы Фазы 0 (`timestamp` и `recvWindow`) этого не затрагивают. **К Фазе 7
  (ордера) выяснить на VST, какой вариант принимает биржа.**
- Клиент `BingXReadOnlyClient` выполняет только GET и только к путям из `READ_ONLY_PATHS`
  (баланс и права ключа). Любой другой путь — `ValueError` до отправки запроса. Торговых
  эндпоинтов в коде нет.
- Ретраев у приватных запросов нет: каждая попытка требует свежего `timestamp`, повтор делает
  человек осознанно.
- Ключ в выводе команды показывается маской (первые и последние 4 символа), секрет не показывается
  никогда. Суммы баланса на боевом контуре скрыты без `--show-balance`.
- Известное ограничение окна подписи: расхождение часов больше `recvWindow` даёт отказ; на
  Windows и в VPS включить синхронизацию времени (chrony на сервере).

## 3. Что осталось уточнить

1. Единица `volume` (база или контракты): для 2026-11-13 09:30 UTC свеча 15m BNB-USDT имела `volume=167.58`. Дешёвая проверка: сравнить с объёмом той же свечи на TradingView `BINGX:BNBUSDT.P` (там объём в монетах). До сверки объём как «число монет» не использовать.
2. Значения кодов в `permissions` (у ключа пользователя `[2]`): сверить с документацией и с ручной проверкой в API Management; до этого коды не интерпретируем.
3. Границы `startTime` и `endTime` для 15m (Фаза 1, при пагинации).
4. Порядок ключей в строке подписи для запросов с параметрами после `timestamp` (Фаза 7, на VST).
5. Гарантирован ли порядок «новые первыми» — на практике проверено на одном запросе.
