# Заметки по API BingX

Каждый факт помечен одной из меток:

- **[проверено запросом]** — получено реальным ответом биржи (лог команды приложен в отчёте);
- **[по документации]** — взято из описания API (официальный репозиторий BingX-API, документация
  docs-v3, SDK) или из сторонних источников; в запросе не проверялось;
- **[не подтверждено]** — источники расходятся или фактов нет.

Состояние на 2026-11-10: рабочий чат работал в окружении без доступа к `open-api.bingx.com`
(DNS не разрешается), поэтому **меток «проверено запросом» пока нет**. Их проставляем после запуска
`uv run squeezelab bingx-smoke` и `bingx-auth-check` у пользователя.

## 1. Публичные свечи (P00-T04)

| Факт | Значение | Метка |
|---|---|---|
| Эндпоинт | `GET /openApi/swap/v3/quote/klines` | [по документации] |
| Базовые адреса | боевой `https://open-api.bingx.com`; запасной домен `.pro` в проекте не используется | [по документации] |
| Ключ | не нужен | [по документации] |
| Формат символа | `BNB-USDT` (дефис) | [по документации] — в примерах SDK и BingX-API/api-ai-skills |
| Параметры | `symbol`, `interval`, `startTime`, `endTime` (мс), `limit` | [по документации] |
| Интервалы | 1m 3m 5m 15m 30m 1h 2h 4h 6h 8h 12h 1d 3d 1w 1M | [по документации] |
| Конверт ответа | `{"code": 0, "msg": "", "data": [...]}`; `code != 0` — ошибка | [по документации] |
| Свеча | объект с шестью именованными полями `open, close, high, low, volume, time` | [по документации], источник — черновик PR #5 в BingX-API/api-ai-skills (ссылается на docs-v3, не принят) |
| Типы | цены и объём — строки, `time` — число (мс, **начало** свечи), поля `closeTime` нет | [по документации], тот же источник |
| Порядок | в образцах новые свечи первыми; гарантии порядка нет | [по документации], тот же источник; **[не подтверждено]** запросом |
| Границы времени | `startTime` включительно, `endTime` исключительно | [по документации]: наблюдение для BTC-USDT 1m в том же PR; на другие пары и интервалы не обобщать |
| Максимальный `limit` | 1440 | [не подтверждено]: 1440 указан для спотовых и coin-M свечей и наблюдался в PR #5 для 1m; для `swap/v3` в найденных текстах официального описания нет |
| Единица `volume` | не определена (база или контракты) | [не подтверждено]: в PR #5 это оспорено; до проверки объём как «число монет» не использовать |
| Незакрытая последняя свеча | политика финальности данных не описана; свеча считается закрытой, если `ts_open + длина ТФ <= сейчас` | [не подтверждено]; правило проекта: формирующуюся свечу отбрасывать |
| Лимиты частоты | рыночные эндпоинты (спот и фьючерсы) делят лимит 500 запросов за 10 с с одного IP | [по документации]: объявление BingX об обновлении лимитов (2025-10-16) |
| Заголовки лимитов | неизвестны | [не подтверждено]; `bingx-smoke` печатает все заголовки со словами limit или retry |

Что клиент делает с этим сейчас (`src/squeezelab/data/bingx_rest.py`):

- парсер принимает только описанную форму (список объектов с шестью полями) и падает с понятной
  ошибкой на любой другой, а не угадывает формат;
- порядок ответа не предполагается: `sort_candles` возвращает новый список по возрастанию `ts_open`;
- ретраи только для GET: сетевые ошибки, HTTP 429 и 5xx, пауза 0,5 с × 2^n, но не дольше 30 с;
  `Retry-After` учитывается (не больше 60 с); ошибки 4xx и `code != 0` в теле не повторяются.

Как закрыть метки (у пользователя, по одной команде):

```bash
uv run squeezelab bingx-smoke --limit 20 --save-raw tests/fixtures/bingx_klines_real.json
uv run squeezelab bingx-smoke --limit 1441     # покажет, режет ли биржа limit выше 1440
uv run squeezelab bingx-smoke --limit 1500
```

Вывод `bingx-smoke` и сохранённый реальный ответ подтверждают или опровергают строки «порядок»,
«незакрытая свеча», «заголовки лимитов», «максимальный limit». Тест парсинга автоматически
подхватит `tests/fixtures/bingx_klines_real.json`.

## 2. Подпись запросов и доступ только на чтение (P00-T05)

| Факт | Значение | Метка |
|---|---|---|
| Адрес демо-среды VST | `https://open-api-vst.bingx.com` | [по документации]: SDK и репозиторий BingX-API/api-ai-skills; запросом не проверен |
| Какой ключ нужен для VST | не определено | [не подтверждено]: источники расходятся. Одни SDK описывают отдельный демо-ключ, другие — ключ основного аккаунта при включённом VST. Выяснится при первом запуске `bingx-auth-check`; результат вернуть в мастер-чат |
| Заголовок ключа | `X-BX-APIKEY: <ключ>` | [по документации] |
| Параметры подписи | бизнес-параметры + `timestamp` (мс) + `recvWindow` (мс, в клиенте 5000) | [по документации] |
| Строка для подписи | `k=v` через `&`, ключи в порядке ASCII, без URL-кодирования | [по документации] |
| Подпись | hex-HMAC-SHA256 от этой строки секретом API, параметр `signature` — последним | [по документации] |
| Баланс | `GET /openApi/swap/v3/user/balance`; в `data` список активов (допускается и одиночный объект с полем `balance`) | [по документации]; форма не подтверждена запросом, парсер понимает обе |
| Актив демо-баланса | `VST` или `USDT` | [не подтверждено]; сводка выбирает USDT, затем VST |
| Права ключа | `GET /openApi/v1/account/apiPermissions` | [по документации]: сторонние обёртки; имена полей ответа [не подтверждено], команда печатает только булевы и целые флаги и предупреждает, если включено что-то похожее на торговлю, перевод или вывод |
| Коды ошибок | в код не зашиты; `code` и `msg` печатаются как есть | сознательно: коды из памяти не использовались |

Заметки по реализации:

- Порядок ключей в строке подписи. В старых официальных примерах `timestamp` дописывается после
  отсортированных бизнес-параметров, в новых справочниках сортируется вместе со всеми. Разница
  проявляется только для ключей, которые по алфавиту идут после `timestamp` (например `type`,
  `workingType`). Запросы Фазы 0 (`timestamp` и `recvWindow`) этого не затрагивают. **К Фазе 7
  (ордера) выяснить на VST, какой вариант принимает биржа.**
- Клиент `BingXReadOnlyClient` выполняет только GET и только к путям из `READ_ONLY_PATHS`
  (баланс и права ключа). Любой другой путь — `ValueError` до отправки запроса. Торговых
  эндпоинтов в коде нет.
- Ретраев у приватных запросов нет: каждая попытка требует свежего `timestamp`, повтор делает
  человек осознанно.
- Ключ в выводе команды показывается маской (первые и последние 4 символа), секрет не показывается
  никогда. Суммы баланса на боевом контуре скрыты без `--show-balance`.
- Известное ограничение окна подписи: расхождение часов больше `recvWindow` даёт отказ; на
  Windows и в VPS включить синхронизацию времени (chrony на сервере).
