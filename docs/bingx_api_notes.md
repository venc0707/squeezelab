# Заметки по API BingX

Каждый факт помечен одной из меток:

- **[проверено запросом]** — получено реальным ответом биржи (лог команды приложен в отчёте);
- **[по документации]** — взято из описания API (официальный репозиторий BingX-API, документация
  docs-v3, SDK) или из сторонних источников; в запросе не проверялось;
- **[не подтверждено]** — источники расходятся или фактов нет.

Состояние на 2026-11-20: строки с меткой **[проверено запросом]** подтверждены запусками пользователя (Windows, без VPN): `bingx-smoke`, `bingx-auth-check` (2026-11-13) и `bingx-probe-klines` (2026-11-20, раздел 4). Рабочий чат сам к BingX не обращался (из его окружения DNS не разрешается).

Что клиент делает с этим сейчас (`src/squeezelab/data/bingx_rest.py`):

- парсер принимает только описанную форму (список объектов с шестью полями) и падает с понятной
  ошибкой на любой другой, а не угадывает формат;
- порядок ответа не предполагается: `sort_candles` возвращает новый список по возрастанию `ts_open`;
- ретраи только для GET: сетевые ошибки, HTTP 429 и 5xx, пауза 0,5 с × 2^n, но не дольше 30 с;
  `Retry-After` учитывается (не больше 60 с); ошибки 4xx и `code != 0` в теле не повторяются.

Оставшиеся непроверенные строки перечислены в разделе 3.

| Факт | Значение | Метка |
|---|---|---|
| Адрес демо-среды VST | `https://open-api-vst.bingx.com`; подписанный запрос принят | [проверено запросом] |
| Какой ключ нужен для VST | **ключ основного аккаунта** из обычного раздела API Management; отдельного раздела или переключателя для демо-ключей нет | [проверено запросом] (запрос принят; со слов пользователя про раздел). Следствие: тот же ключ действителен и на боевом контуре, поэтому ключ обязан быть только на чтение |
| Заголовок ключа | `X-BX-APIKEY: <ключ>` | [проверено запросом] |
| Параметры подписи | бизнес-параметры + `timestamp` (мс) + `recvWindow` (мс, в клиенте 5000) | [проверено запросом] для запроса без бизнес-параметров |
| Строка для подписи | `k=v` через `&`, ключи в порядке ASCII, без URL-кодирования | [проверено запросом] для `recvWindow` и `timestamp`; с другими параметрами не проверялось |
| Подпись | hex-HMAC-SHA256 от этой строки секретом API, параметр `signature` — последним | [проверено запросом] |
| Баланс | `GET /openApi/swap/v3/user/balance`; на VST в `data` один актив `VST`, поля `balance`, `equity`, `availableMargin` (100000.0000) | [проверено запросом]; форма (список или объект) парсером принята, какая именно — не фиксировалась |
| Актив демо-баланса | `VST` | [проверено запросом] |
| Права ключа | `GET /openApi/v1/account/apiPermissions`: ответ без поля `code`, плоский объект `{permissions: list[int], ipAddresses: list, note: str, apiKey: str}`. У ключа пользователя на VST: `permissions=[2]`, `ipAddresses=[]`. Ручная проверка в API Management (2026-11-14): включено только «Чтение»; торговля (спот и бессрочные фьючерсы), Universal Transfer, вывод, управление субаккаунтами и P2P выключены | [проверено запросом] форма и значения; [проверено вручную] права ключа. Соответствие «код `2` = только чтение» — **одно наблюдение, не документация**; остальные коды не расшифрованы. Команда печатает значения (целые и списки целых; строки `note` и `apiKey` скрыты) и напоминает про ручную проверку, выводов о правах не делает |
| Коды ошибок | в код не зашиты; `code` и `msg` печатаются как есть | сознательно: коды из памяти не использовались |

Заметки по реализации:

- Порядок ключей в строке подписи. В старых официальных примерах `timestamp` дописывается после
  отсортированных бизнес-параметров, в новых справочниках сортируется вместе со всеми. Разница
  проявляется только для ключей, которые по алфавиту идут после `timestamp` (например `type`,
  `workingType`). Запросы Фазы 0 (`timestamp` и `recvWindow`) этого не затрагивают. **К Фазе 7
  (ордера) выяснить на VST, какой вариант принимает биржа.**
- Клиент `BingXReadOnlyClient` выполняет только GET и только к путям из `READ_ONLY_PATHS`
  (баланс и права ключа). Любой другой путь — `ValueError` до отправки запроса. Торговых
  эндпоинтов в коде нет.
- Ретраев у приватных запросов нет: каждая попытка требует свежего `timestamp`, повтор делает
  человек осознанно.
- Ключ в выводе команды показывается маской (первые и последние 4 символа), секрет не показывается
  никогда. Суммы баланса на боевом контуре скрыты без `--show-balance`.
- Известное ограничение окна подписи: расхождение часов больше `recvWindow` даёт отказ; на
  Windows и в VPS включить синхронизацию времени (chrony на сервере).

## 3. Что осталось уточнить

1. Единица `volume` (база или контракты): значение совпало с TradingView, но масштаб в BNB или в USDT окончательно подтвердит только сверка суммы сделок с минутным `volume` (P01-T05, приёмка 3).
2. Значения кодов в `permissions`: для ключа только на чтение наблюдалось `[2]` (одно наблюдение). Остальные коды сверить с документацией до Фазы 7, когда появится торговый ключ; жёсткого сравнения в код не закладываем.
3. Порядок ключей в строке подписи для запросов с параметрами после `timestamp` (Фаза 7, на VST).
4. Гарантирован ли порядок «новые первыми»: наблюдался во всех запросах пробы, гарантий биржи нет.
5. Окно хранения по ТФ для других пар и точные пределы для 1m, 1h и 1d (раздел 4, «Скользящее окно хранения»): выяснит P01-T06 и ежедневная докачка.
6. Расхождение high/low с TradingView для свечи 2026-11-13 09:30 UTC: на присланном скриншоте рядом со свечой линии 637.42 и 635.66 при `high=637.41`, `low=635.65` из API. Если это high и low свечи в TradingView, фиды различаются на 0.01 (важно для сверки детектора в Фазе 2); если это линии индикатора, расхождения нет.

### Скользящее окно хранения и первая загрузка (сервер, 2026-11-22)

Первая загрузка BNB-USDT на сервере (`data download`, `/srv/data/squeezelab`, 5 запросов в секунду) и сравнение с пробой `--set depth` суток раньше показали, что **история 15m и 4h скользит**:

|---|---|---|---|---|

[проверено запросом] Для 15m начало сдвинулось на одну свечу за те минуты, что шла загрузка, а число свечей в окне осталось 9600 (на момент depth было 9615, обрезка, видимо, выполняется не на каждой свече). Для 4h начало сдвинулось на сутки при ожидаемых 20 часах, окно 9000 свечей. Это совпадает с гипотезой «биржа хранит ограниченное число свечей на ТФ: 15m около 9600 (100 суток), 4h около 9000 (1500 суток), старые удаляются». Для 1m, 1h и 1d такого предела не видно (начало не сдвинулось), но он может быть выше. Правила, которые из этого следуют:

- окно `[start, end)` с `startTime` и `endTime`: `start <= время открытия < end`; при превышении предела остаются самые новые свечи;
- `endTime` без `startTime`: округляется вверх до границы свечи, свеча на границе входит; загрузчик этой формой не пользуется;
- предел ответа зависит от ТФ (15m: 1000; 1m: не меньше 1440); окно в 1000 баров безопасно для обоих.

Что загрузчик (`src/squeezelab/data/downloader.py`) делает с этим:

- запрашивает окна `[start, end)` по `WINDOW_BARS = 1000` баров встык, поэтому окно не усекается; размер настраивается (`--window-bars`);
- не доверяет числу свечей: полнота окна проверяется по набору меток времени, до трёх попыток;
- границу «закрытая свеча» берёт по часам машины и по самой новой свече биржи (она формирующаяся), выбирая более раннюю;
- порядок ответа не использует.

Если при `--start` раньше начала истории биржа отдаёт пустой ответ, загрузчик сам ищет начало истории бисекцией (`data/history.py`) и начинает период с самой ранней свечи, о чём предупреждает в отчёте.
